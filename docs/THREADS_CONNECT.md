# Подключение Threads: один вход владельца, затем проверка оператором

Собственный аккаунт: stanislav.web. Поиск Threads использует официальный API
Meta напрямую, без подписки Postiz. Публикации остаются отдельным подключением
Postiz и отдельным одобрением каждой версии; этот шаг сам ничего не публикует.

## Действие владельца

1. Открыть https://developers.facebook.com/apps/ и войти своим аккаунтом.
2. Выбрать существующее приложение с Threads API или создать приложение для
   использования Threads API. Официальная инструкция:
   https://developers.facebook.com/docs/threads/get-started/ .
3. В настройках Threads API подключить свой stanislav.web; если dashboard требует
   роль тестировщика/подтверждение приглашения, пройти это своим аккаунтом Threads.
4. Получить пользовательский access token. Для проверки профиля нужен
   threads_basic, для поиска — threads_keyword_search. Наличие basic не означает,
   что доступен поиск: уровень доступа и разрешения проверяются реальным запросом.
5. Внести token в защищённое поле THREADS_ACCESS_TOKEN настроек облачной среды.
   Требование поля уже сохранено в draft, destination — graph.threads.com.
   Токен не присылать в чат и не вставлять в JSON источников или исходники сайта.
6. Сохранить настройки среды и опубликовать конфигурацию. Draft сам не применяет
   значения или сетевой доступ. Если Meta не даёт нужный scope, показать название
   шага/ошибку без токенов; не заявлять доступ полученным до фактической проверки.

App secret не требуется для проверки уже выданного пользовательского токена.
Локальный OAuth callback/backend для этого пути не создаётся. Владелец выполняет
вход и выдачу прав; оператор не располагает браузерной сессией его Meta-аккаунта.

## Действия оператора после появления доступа

```bash
.venv/bin/python scripts/connect_threads.py --check-search
```

Скрипт делает только GET /v1.0/me?fields=id,username, сверяет stanislav.web, затем
GET /v1.0/keyword_search с одной записью и запросом «нужен сайт». Ключ передаётся
в Authorization только фиксированному HTTPS origin; redirects не выполняются.
Ошибки не выводят токен/сырой ответ. Код0 означает PROFILE_CONNECTED (без опции)
или SEARCH_CONNECTED (с опцией). NEEDS_TOKEN/ACCOUNT_MISMATCH/ошибки — код2.

Только после SEARCH_CONNECTED оператор сохраняет THREADS_REVIEW_CONFIRMED=true,
настраивает query в connector_configs, включает threads_search и перезапускает
свой worker с актуальными runtime credentials. Название legacy-флага не заменяет
фактический scope/API-доступ. Для своего dev/test аккаунта требования Meta могут
отличаться от подключения внешних пользователей — проверять dashboard и API.
Токен может иметь срок действия; срок/обновление определяется Meta, без обещания
постоянного доступа и без выдуманного refresh token.

Пример конфигурации одного тестового поиска: {"query":"нужен сайт"}. После одного
настоящего результата проверяются URL, свежесть, дедупликация и карточка владельцу.
Это не означает автоматический поиск по всем услугам/всем соцсетям.

## Текущий результат

6 изолированных проверок verifier прошли на HTTP mocks. Реальный запуск вернул
NEEDS_TOKEN: в runtime/vault THREADS_ACCESS_TOKEN пока отсутствует. Custom network
hosts в действующей среде пусты; сохранённый разрешающий draft ещё не применён.
Настоящий GET профиля/поиск и публикации не выполнялись.
