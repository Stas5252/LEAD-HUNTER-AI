# LEAD HUNTER AI: спецификация первого рабочего этапа

Дата: 15 октября 2026 года. Статус: согласована пользователем; результат этапа A описан в docs/VERIFICATION.md.

## Цель и границы

Создать систему для одного русскоязычного веб-разработчика: находить подтверждаемые
запросы на сайты, магазины, Telegram-ботов, автоматизацию и AI-видео, оценивать
релевантность и готовить персональные предложения. Основной рынок — Россия.
Критерий качества — релевантность и проверяемое основание потребности.

Источник требований — приложенный LEAD_HUNTER_AI_CODEX_PROMPT.md. Сначала
реализуется его этап A. Все девять способов привлечения сохраняются в реестре
источников и дорожной карте; наличие строки в реестре не означает готовую интеграцию.
Реальный поиск, публикации и отправка предложений не считаются проверенными на
основании работы DEMO.

## Рассмотренные варианты

1. **n8n + PostgreSQL, стандартные ноды и небольшие адаптеры — выбран.**
   Редактор сценариев, расписания, HTTP и Telegram предоставляет n8n.
   Дедупликацию, состояния и атомарные ограничения обеспечивает PostgreSQL.
   Это минимальный вариант, соответствующий требованию о готовых компонентах.
2. Python-бот + PostgreSQL + n8n. Удобнее сложные диалоги, но появляется отдельное
   приложение и дублируется оркестрация. Для первого этапа не требуется.
3. Одновременное развёртывание Postiz, NocoDB и браузерного краулера. Даёт больше
   интерфейсов, но увеличивает расход ресурсов и объём непроверенных интеграций.
   Подключается по отдельным задачам после проверки основы.

## Архитектура первого этапа

Docker Compose запускает PostgreSQL и n8n. В одной инсталляции PostgreSQL
используются разные базы и роли для метаданных n8n и прикладных данных.
Прикладная роль не получает прав суперпользователя. Порты редактора и БД
по умолчанию привязаны к loopback; внешний Telegram webhook открывается
через документированный HTTPS reverse proxy, отдельно от редактора.

Основной поток:

    DEMO JSON/CSV или разрешённый импорт
      -> нормализация и проверка доказательств
      -> стабильный ключ и дешёвая классификация
      -> необязательная OpenAI-оценка
      -> PostgreSQL UPSERT
      -> карточка в тестовом выводе или Telegram администратора

Настоящие компании не придумываются. Каждая фикстура содержит is_demo=true;
карточка и тестовый вывод явно помечаются «DEMO: вымышленный пример».
Отсутствие website в исходной строке означает UNKNOWN, а не ABSENT_CONFIRMED.

Небольшие скрипты обслуживают настройку, импорт workflow и проверки. Постоянного
самописного HTTP backend, собственной CRM и отдельного брокера очередей в MVP нет.

## Workflow и интерфейсы

1. **Импорт лидов:** ручной запуск DEMO и JSON/CSV импорт, единая нормализация,
   лимит записей, классификация, UPSERT и выдача карточек. Импорт извне защищён
   аутентификацией и проверкой схемы. Произвольные URL автоматически не скачиваются.
2. **Telegram-пульт:** обработка команд и inline callback; проверка точного
   admin user ID и разрешённого private chat до обращения к данным и действий.
   Поддерживаются /start, /today, /find, /leads, /lead, /draft, /approve, /reject,
   /sources, /stats, /budget, /stop и /resume. В /find сразу видны доступные
   источники; DEMO нельзя спутать с настоящим поиском.
3. **Оценка OpenAI:** Responses API, JSON Schema, валидация ответа, таймаут и
   ограниченные повторы. При отсутствии ключа — детерминированная эвристика с
   пометкой метода оценки. Ошибка API не превращается в успешную AI-оценку.
4. **Очередь уведомлений:** доставка карточек только владельцу, лог попыток,
   ограниченный backoff, отсутствие бесконечных повторов.

Telegram по умолчанию можно подключить через long polling с сохраняемым offset,
без публичного домена. Отдельно документируется webhook с HTTPS и secret header;
polling и webhook не работают одновременно. Выбранный транспорт проверяется на
тестовых Telegram payload; настоящий Bot API требует токена и разрешения владельца.

Указанный шаблон n8n 15411 должен быть получен и проверен до заявления об адаптации.
Его платные провайдеры заменяются DEMO-источником, сохраняется документированный
полезный поток. Если получить шаблон не удастся, предоставляется собственный
импортируемый workflow со стандартными нодами и явно фиксируется отклонение.

## Данные и переходы состояний

Таблица leads содержит все поля из исходного задания:
lead_id, created_at, last_seen_at, source, source_url, company_name, niche, city,
website, website_status, public_contact, contact_source_url, need_detected,
proof_quote, score_0_100, confidence_0_1, why_relevant, offer_type, draft_message,
status, next_action, next_followup_at, owner_approved, estimated_cost, attribution,
tags. Дополнительно нужны is_demo, source_type, dedupe_key, content_hash,
scoring_method и версия черновика.

Ключ дедупликации выбирается по приоритету: идентификатор компании в источнике,
каноническая ссылка запроса, нормализованный подтверждённый домен, затем
детерминированный ключ компании и города. Строки без устойчивой идентичности
отправляются на ручную проверку. Социальный домен целиком не является ключом
компании. Нормализация телефонов не превращает неопределённый номер в российский.
Повторный импорт обновляет last_seen_at, не снимает DNC и не повторяет уведомление.

Дополнительные таблицы: source_registry, app_settings, processed_updates,
lead_events, action_approvals, notification_outbox, llm_cache, daily_usage,
schema_migrations. Миграции версионируются и применяются повторно безопасно.

Статусы: NEW, REVIEW, APPROVED, CONTACTED, REPLIED, NEGOTIATION, WON, LOST, DNC.
Классы: DIRECT_REQUEST, LIKELY_NEED, PARTNER, COMPETITOR, IRRELEVANT.
Классификация отделена от статуса сделки и числового score.

## Одобрения, остановка и доступы

/approve относится к конкретному действию и версии черновика; изменение текста
аннулирует прежнее одобрение. В этапе A внешних каналов отправки КП нет:
одобрение записывает решение, а отправка остаётся ручной. Нельзя отображать
CONTACTED только потому, что владелец нажал «Одобрить».

/reject переводит лид в DNC и отменяет ожидающие действия. /stop сохраняет
глобальную остановку для сборщиков, AI-вызовов и очередей; /resume доступен
только владельцу. Проверка остановки повторяется перед внешним действием.
Уже принятый внешним сервисом запрос отменить гарантированно невозможно.

Повторный Telegram update не повторяет побочные эффекты. Telegram не предоставляет
универсальной гарантии exactly-once для sendMessage: неоднозначный сетевой исход
не вызывает слепую повторную отправку, а записывается для проверки.

Тексты карточек экранируются, SQL использует параметры, секреты не попадают в
репозиторий и логи. Текст лида — недоверенные данные, он не получает инструментов,
не изменяет системные правила и не разрешает действия через подсказки для LLM.
Будущий аудит сайтов обязан блокировать loopback, private/link-local IP и опасные
перенаправления, прежде чем разрешать автоматическую загрузку URL.

## Бюджет и отказоустойчивость

Начальные значения: AUTOPUBLISH=false, AUTO_OUTREACH=false,
VIDEO_GENERATION_PAID=false, DAILY_API_BUDGET_USD=1,
MAX_LLM_CALLS_PER_DAY=50, MAX_LEADS_PER_RUN=100, MAX_PUBLIC_POSTS_PER_DAY=2.

Перед LLM-вызовом PostgreSQL атомарно резервирует вызов и консервативную оценку
стоимости по настройкам цены и максимальным входным/выходным токенам. Повторы
тоже расходуют резерв. Без конфигурации цены и лимитов реальные вызовы отключены.
Кэш привязан к hash(content), модели, версии схемы и промпта. Нельзя одновременно
выдать двум процессам последний доступный бюджет. Фактический биллинг провайдера
остаётся источником истины; долларовая защита обозначается приблизительной.

Compose включает healthcheck, restart policies, постоянные тома и ограничение
логов. Проверяются backup и восстановление прикладной БД; отдельно сохраняется
ключ шифрования n8n. Версии образов фиксируются после проверки доступности и
совместимости, включая ARM64. Обещания о бесплатной доступности Oracle нет.

## Артефакты и приёмка

Ожидаемые файлы: docker-compose.yml, .env.example, .gitignore, README.md,
START_HERE.md, docs/SOURCES_AND_DECISIONS.md, docs/STATUS.md, миграции,
workflows/*.json, scripts/*, tests/* и fixtures/*.

Проверки этапа A:

1. compose config и доступность закреплённых образов; реальные healthcheck.
2. Миграции на чистой БД и повторный запуск без потери данных.
3. Импорт workflow именно в запускаемую версию n8n; запуск основного workflow
   через n8n, а не только отдельной копии JavaScript-функции.
4. JSON и CSV фикстуры дают ожидаемые лиды в PostgreSQL; повторный импорт не
   создаёт дубликаты, не сбрасывает DNC и не создаёт повторное действие.
5. Проверка DIRECT_REQUEST/COMPETITOR/IRRELEVANT, UNKNOWN для отсутствующего
   поля сайта, доказательства и DEMO-маркера в конечной карточке.
6. Telegram payload: команды, inline callback, чужой user ID, повторный update,
   устаревшее одобрение и остановка. Без токена — только явно обозначенный mock.
7. OpenAI mock: корректная схема, повреждённый JSON, таймаут, rate limit,
   токенный лимит, кэш и конкурирующие попытки исчерпать дневной бюджет.
8. Отсутствие исходящего КП без подходящего канала и конкретного одобрения;
   одобрение само не меняет состояние на CONTACTED.
9. Перезапуск собственных контейнеров сохраняет данные и настройки остановки.
10. Инструкция позволяет повторить DEMO без API-ключей. Настоящая доставка в
    Telegram проверяется отдельно после безопасного подключения токена владельцем.

Итоговый отчёт различает выполненные, проваленные, пропущенные и недоступные
проверки. Реальные источники, Meta и публикации не обозначаются WORKS по мокам.

## Установка, подключение и ограничения

Для DEMO потребуются только локальные пароли БД и ключ шифрования n8n:
setup-скрипт создаёт их криптографически и сохраняет в игнорируемом .env с
ограниченными правами, не перезаписывая существующие значения.
Внешние ключи и идентификатор администратора владелец добавляет самостоятельно
через защищённые настройки или локальный .env; в чат секреты не запрашиваются.

README содержит Ubuntu и Windows Docker Desktop, команды запуска/остановки,
первую настройку n8n, привязку credentials без секретов в workflow JSON,
опциональный HTTPS webhook, backup/restore и таблицу расходов с допущениями.
Для будущих облачных задач сохраняются проверенные install_script/start_skill;
используется существующий checkout, дополнительный Git worktree не нужен.

Открытое внешнее ограничение: нужно разрешить доступ к официальным страницам
документации и шаблона, если политика останется прежней. Это не препятствует
написанию DEMO, но препятствует честному подтверждению адаптации шаблона 15411.
